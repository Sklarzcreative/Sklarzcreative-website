## What was fixed

**The privacy page's third-parties grid had a solid grey block in it.**

`.write-in` draws its dividers by letting a grey container background show
through 1px gaps, which works only while every cell has a child painting
`--paper` over it. Adding the Google Analytics card took the page to three
cards, so at the two-column breakpoint the fourth cell had no child and rendered
grey.

Fixed twice on purpose:

1. **Content.** The "hosted on GitHub Pages" note was a loose paragraph under
   the grid. It is now the fourth card — which fills the cell and is more honest,
   since GitHub Pages *is* another party the browser talks to.
2. **Structure.** The grid now paints `--paper` and gives each card a 1px ring,
   so an empty cell stays paper no matter how many cards a page has. The
   original bug can't recur at five cards, or seven.

Verified in Chromium: grey block gone, dividers still single 1px lines, the
Scorecard's four-card grid unchanged, a deliberate three-card test clean, and
print rendering intact — which mattered, because the Scorecard is designed to be
printed and `print-color-adjust: exact` is already set for both techniques.

## What was checked and passed

**Load-bearing rules 1 and 3** (static): every page opens with a dark section;
no `.page-hero` carries `.is-dark`.

**Load-bearing rules 4 and 5** (browser): every page loaded with JavaScript
disabled renders full static content with no hidden reveal blocks; every page
under `prefers-reduced-motion: reduce` resolves every reveal to its final state.
These two matter most because they fail invisibly — rule 4 only when JS breaks,
rule 5 only for readers who asked for less motion, who are the least likely to
tell you.

**Everything else**: no broken internal links, no missing alt text, canonicals
present and on the apex, titles and descriptions present, exactly one `h1` per
page, the privacy link on all 14 pages, two-way sitemap agreement, no horizontal
overflow at 360px or 1280px, no uncaught page errors.

## The part worth reading: two findings that were wrong

Both scripts started out reporting problems that were not problems. Recording
this because the next person to run them will get a list and be tempted to work
through it.

**Twenty static findings, all false.** The first run flagged `Index.html`,
`insights/the-trust-files/trust-is-not-a-vibe.html` and
`docs/og-card-template.html` for missing `h1`s, descriptions, canonicals and
sitemap entries. All three are correct files: the first two are deliberate
redirect stubs with `robots: noindex`, a proper canonical, meta-refresh, JS
`location.replace`, and a no-JS fallback link. Adding an `h1` and a meta
description to a redirect stub is not a fix — it is damage.

The audit now excludes stubs by **behaviour** (refresh or `location.replace`
plus `noindex`), not by file size, so a stub that grows is still recognised.

**"37 of 40 reveal blocks hidden on mobile."** Alarming, and wrong. With JS on
and motion enabled, reveal blocks are *supposed* to start hidden and animate in
on scroll — that is the motion system in [04](./04-motion-language.md) doing its
job. Counting them without scrolling measures the design, not a defect.

Confirmed by scrolling the homepage at 360px: **40 hidden before, 0 after.** The
scroll pass is now part of the browser audit, because it is the only honest way
to check that lane.

The general rule both taught: **confirm a finding is real before acting on it**,
especially when the check is mechanical. A script that produces a tidy list is
persuasive in a way that has nothing to do with being right.

## Two traps in the tooling itself

- `waitUntil: 'networkidle'` **hangs indefinitely** behind an egress proxy,
  because the Google Fonts request never settles. The browser audit aborts
  external requests and waits on DOM readiness instead. The full sweep now takes
  about 40 seconds; before this it ran for over ten minutes without finishing.
- The tag push `git push origin <tag>` is rejected by this remote. The restore
  point is therefore a **branch**, `pre-editorial-audit-2026-08-25`, which
  matches the existing `pre-luxury-redesign-2026-08-22` convention anyway.
