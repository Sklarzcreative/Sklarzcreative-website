# Runbook B · The publisher

> Approved queue row → platform route → retrieve asset → publish → capture the
> published URL → stamp the status.
>
> Historically **SC-03 Sklarz Scheduled Publisher**.

**The governing rule, which this runbook exists to encode:**

> **Reliability outranks reach. A route that verifiably works beats three that
> might.**

This system has already had one publishing-reliability incident. The expensive
part of that class of failure is not the missed post — it is the backlog it
creates, which then tempts someone into a bulk release, which is the second and
larger incident. Every design choice below is downstream of that.

---

## Trigger

| | |
| --- | --- |
| Module | **Scheduler** |
| Interval | every 15 minutes |
| Why not a Sheets watch | A schedule is idempotent and observable: if it stops running, the *absence* is visible in Make's execution history. A watch that silently stops watching looks exactly like a queue with nothing in it, which is precisely the failure that hurt before. |

## Step 1 · Select what is due

| | |
| --- | --- |
| Module | **Google Sheets · Search Rows** |
| Spreadsheet | `Sklarz_Creative_Make_Automation_Content_Engine` — select it by name in the module. The id is deliberately not recorded in this public repository; see [architecture.md](../architecture.md#why-the-spreadsheet-id-is-not-in-this-repository). |
| Sheet | `MAKE - Publish Queue` |
| Filter | `status` = `APPROVED` **AND** `scheduled_at` ≤ `{{now}}` **AND** `published_url` is empty |
| Sort | `scheduled_at` ascending |
| **Limit** | **5** |

### Why the limit is five and must stay small

A limit is a blast-radius control, not a performance setting. If something is
wrong — a bad template, an expired token, a mis-set date that made forty rows
due at once — five is the number of public mistakes made before the next run,
and the next run is fifteen minutes away. Raising this to 50 converts a
recoverable error into an incident.

Add a filter immediately after:

| | |
| --- | --- |
| Label | `route is production-ready` |
| Condition | `platform` **in** the onboarded set |

Maintain that set explicitly in the scenario, not implicitly by which
connections happen to exist. As of 24 August 2026 it is:
`linkedin`, `linkedin_company`, `instagram`, `facebook`, `threads`, `x`,
`pinterest`.

**`tiktok`, `youtube` and `bluesky` are NOT in the set.** They have not passed
[route onboarding](./route-onboarding.md). A credential existing is not a route
working.

## Step 2 · Claim the row

**Before doing anything platform-facing**, set `status = PROCESSING` and
`updated_at = {{now}}`.

This is the single cheapest reliability mechanism in the whole system:

- Two overlapping runs cannot both publish the same row, because the second
  selection no longer matches `status = APPROVED`.
- A run that dies mid-flight leaves a `PROCESSING` row with an old
  `updated_at`, which is a visible, diagnosable trace. Without the claim, a
  dead run leaves a row that looks untouched and simply never goes out —
  **silence, which is the dangerous failure mode.**

## Step 3 · Route by platform

**Router**, one route per platform, each with an exact-match filter on
`platform`. Add a final **fallback route** whose only job is to write
`status = FAILED` and `error = "no route for platform <value>"`. A row that
matches no route must not vanish into a successful-looking run.

## Step 4 · Retrieve the asset, where one is required

| | |
| --- | --- |
| Module | **Google Drive · Download a File** (or the platform's own upload step) |
| Source | `asset_ref` |

Platforms that cannot publish without media: **Instagram, Pinterest** (and
TikTok, YouTube once onboarded).

If `asset_ref` is empty or the download fails on such a platform:
`status = FAILED`, `error = "missing or unresolvable asset"`, and **stop that
route**. Never publish a media post without its media — a text-only Instagram
post is a public mistake, and it cannot be quietly fixed.

The reliability agent detects an empty `asset_ref` **before** the scheduled
time, which is the only point at which the information is still useful. That
check is the cheap one; this one is the last line.

## Step 5 · Publish

The platform module, per route. Two rules that apply to every route:

1. **The link comes from `target_url` unchanged.** It was generated by
   [`lib/utm.mjs`](../lib/utm.mjs) when the pack was staged. The publisher never
   composes, appends to, or re-tags a URL — a UTM assembled at publish time is
   an attribution bug nobody will find.
2. **`alt_text` is passed wherever the platform accepts it.** Not optional.

## Step 6 · Capture the published URL — the non-negotiable step

On success, write **both**:

| Field | Value |
| --- | --- |
| `published_url` | the URL or permalink the platform returned |
| `published_at` | `{{now}}` |
| `status` | `PUBLISHED` |
| `updated_at` | `{{now}}` |

**Never stamp `PUBLISHED` without a `published_url`.** A row in that state is
unverifiable: it may have published, it may have failed silently, and there is
no way to tell afterwards. The reliability agent treats it as a critical
finding and never counts it as a success — so a route that cannot return a URL
is a route that reports as permanently degraded, which is the correct incentive.

If a platform genuinely cannot return a permalink, that fact belongs in the
route's onboarding record, and the route publishes a constructed profile URL
plus a note — not an empty field, and not a green status.

## Step 7 · On failure

`status = FAILED`, `error` = **the platform's response verbatim**,
`attempt_count` incremented, `updated_at = {{now}}`. Then
[runbook C](./make-c-failure-handling.md).

**Keep the error text verbatim.** The exact wording is what identifies the
cause — "401 Unauthorized" and "403 Forbidden: insufficient scope" lead to
different fixes, and a summarised "publish failed" discards the only evidence
you had.

---

## Success state

```
status = PUBLISHED  AND  published_url is not empty  AND  published_at is set
```

All three. Anything less is not a success, however green it looks.

## Error states

| State | Meaning |
| --- | --- |
| `FAILED` + `error` | The publisher tried and gave up. **Loud, therefore the less dangerous kind.** |
| `PROCESSING` / `SENDING` with an old `updated_at` | A run died mid-flight. |
| `APPROVED`, past its time, no error, no URL | **The silent failure.** The publisher did not run or ran and said nothing. This is the one that produced the incident. |
| `PUBLISHED` with no `published_url` | Unverifiable. Never a success. |

## Idempotency

**Key: `content_id` + `platform` + `scheduled_at`**, written to
`idempotency_key` when the row is created.

Two independent defences, because one is not enough:

1. **The claim in step 2.** `status = PROCESSING` removes the row from the
   selection filter, so a concurrent or overlapping run cannot pick it up.
2. **The key check before publishing.** If another row shares this
   `idempotency_key` and already has a `published_url`, do not publish — write
   `status = CANCELLED`, `error = "duplicate of <row_id>"`.

The retry path in runbook C is retry-**by-row**, never re-select-and-republish.
A retry that re-queries the queue can pick up a row that succeeded but whose
status write failed, and publish it twice.

## Logging

Per row, per attempt: `row_id`, `content_id`, `platform`, `scheduled_at`,
`attempt_count`, the platform's response status, the `published_url` (or the
verbatim error), and the timestamps of the claim and the final write.

## Manual recovery

**A backlog exists. Read this before touching anything.**

```
1. Pick ONE overdue item. Prefer the least time-sensitive one.
2. Publish that single row through the normal route — one row, by hand or a
   single-row run.
3. Verify BOTH that a published_url came back AND that the post is visible on
   the platform. Look at it. The URL is not the proof; the post is.
4. Only then release current content — the pieces that are still timely.
5. Then decide item by item which stale items are still worth posting.
   Most are not. A backlog is usually evidence, not inventory.
```

**Do not run the whole queue.** Releasing a backlog into a route that is still
broken produces nothing and hides the diagnosis. Releasing it into a route that
has just been fixed produces a flood of out-of-date posts under a founder's
name. Neither is recoverable, and the second is worse than the silence it was
meant to fix.

Full procedure, including how to decide what to abandon:
[incident recovery](./incident-recovery.md).
